# ApplyPilot AI — Security, Privacy & Compliance Architecture

---

## 1. Security Control Matrix

| Area                        | Required Protection                                                                                                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authentication**          | Secure session/JWT management (`SECRET_KEY`), per-user authorization checks on every FastAPI route                                                                                            |
| **API Keys & Secrets**      | Encrypted at rest (`ENCRYPTION_KEY`) or OS credential store; **never** in `.env.example`, Git, frontend bundles, or LLM prompts                                                               |
| **Resume & Artifact Files** | Private `storage/` directories with path-traversal protection, user ownership checks (`404`), and SHA-256 download integrity verification (`409` on mismatch or unvalidated/failed artifacts) |
| **Gmail Integration**       | OAuth2 with minimum required scopes (`gmail.send` / read-only confirmation matching if enabled)                                                                                               |
| **Database**                | Least-privilege DB credentials, encrypted backups, strict per-user row scoping                                                                                                                |
| **Browser Automation**      | Isolated Playwright contexts, strict domain allowlists, no cookies/passwords exposed to LLMs                                                                                                  |
| **LLM Inputs**              | Sensitive-data minimization and prompt-injection delimiters                                                                                                                                   |
| **Submission Integrity**    | Unique idempotency keys, LangGraph `interrupt()` approval gate, post-submit verification                                                                                                      |
| **Logging**                 | Automatic PII, token, and credential redaction in all application & LLM router logs                                                                                                           |
| **Workflow Auditability**   | Immutable `approval_records` and `audit_logs` capturing who approved, which resume checksum, and verification proof                                                                           |

## 2. Threat Mitigations & Hard Boundaries

### 2.1 Prompt Injection Defense

- All external text—job descriptions, career pages, company research snippets, and emails—must be treated strictly as **untrusted data**, never as instructions.
- External content is wrapped in explicit data delimiters and never granted tool-execution authority or permission to alter submission policy, eligibility thresholds, or approval states.
- All tool permissions and policy decisions execute in deterministic Python code.

### 2.2 Resume Fact Protection

- Every claim, technology, date, metric, and project bullet generated by `ResumeTailoringAgent` must trace back to a verified record in `CandidateProfile` (`FactualValidatorAgent`).
- Cross-project technology leakage, `planned_features` promotion, unverified skills, altered education/experience dates/GPAs, and invented metrics are deterministically rejected before any PDF is rendered.
- `ResumeJobMapping` is the sole canonical approval store (`pending_review` -> `approved` | `rejected`), enforced transactionally (`SELECT ... FOR UPDATE`), with master resumes excluded from regeneration/approval/rejection and downstream submission services required to call `require_approved_tailored_resume_for_submission` server-side.

### 2.3 Application Answer Protection

- Never guess or hallucinate answers to legal eligibility, work authorization, visa sponsorship, salary expectations, disability/veteran declarations, or background questions.
- Unknown questions pause the Application Subgraph in `NEEDS_USER_INPUT` until the candidate provides a verified answer.

### 2.4 Platform Terms, CAPTCHA & LinkedIn Boundary

- **LinkedIn:** Strictly prohibited from building unauthorized LinkedIn scrapers or automating LinkedIn login, search extraction, or Easy Apply bots. Use permitted discovery methods and direct the user to LinkedIn manually when needed.
- **Anti-Bot / Security Gates:** Never bypass CAPTCHAs, MFA challenges, login walls, or rate limits. Immediately transition to `MANUAL_ACTION_REQUIRED` and notify the user.
- **Public APIs:** Presence of a public listing endpoint (e.g., Greenhouse Job Board API or Lever Postings API) does **not** imply candidate submission rights; auto-submit only when explicitly authorized.

### 2.5 Reliability & Failure Recovery

- Bounded retries with exponential backoff and circuit breakers on failing external connectors/LLM providers.
- Post-timeout submission rule: if a network timeout occurs after submitting, **verify submission status first** before any retry.
- Global `PAUSE_ALL_SUBMISSIONS` and emergency-stop flag checked before every submission action.
